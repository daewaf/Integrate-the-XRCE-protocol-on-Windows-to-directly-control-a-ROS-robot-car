# C#/WPF 代码编写与风格规范

> 版本：1.1（2026-10-26）。本文包含初稿规则和经讨论确认的补充，可作为 AI 辅助开发 C#/WPF 程序的执行规范。
>
> 本文随 csharp-wpf-development skill 独立分发。项目接入及迁移边界见 [接入说明](adoption.md)，按实际项目补充确认的问题见 [项目场景](project-scenarios.md)。

## 1. 适用范围与技术选型

### 1.1 适用方式与迁移边界

- 新项目执行本规范。
- 已有项目采用本规范时，应安排一次覆盖人工维护代码的统一风格迁移，包括排版、命名、注释等。复制规范资料不代表迁移完成；开发、只读审查和统一迁移按本次任务范围执行，普通功能任务不自动夹带全库修改。用户明确要求统一迁移时，完成指定范围内的迁移，不缩减为只改新增代码。
- 涉及架构更新、框架升级或实质性重构时，采用渐进方式，根据当前任务需要调整，不因风格迁移自动扩大到整体架构改造。
- 风格迁移以保持程序行为和兼容性为前提。命名修改涉及 XAML 绑定、反射、序列化、持久化数据或公开接口时，应检查引用与外部契约；会改变契约的修改按实质性重构处理。
- 自动生成代码和第三方代码不纳入人工风格迁移。

### 1.2 目标框架

- 新项目未指定目标框架时，优先使用 .NET 10；WPF 使用相应的 Windows 目标框架，例如 `net10.0-windows`。
- 已有项目沿用现有目标框架，升级作为单独的技术调整处理。

## 2. 架构、文件与类型组织

### 2.1 架构原则

- 在可以选择的情况下，优先采用简单架构，避免复杂设计。
- 小型、轻量项目优先采用 code-behind（代码隐藏）配合功能类：界面事件和交互放在代码隐藏中，独立的功能处理放在功能类中。
- 当界面状态、交互或复用需求变得复杂时，再引入轻量 MVVM；不以固定行数或窗口数量机械决定是否使用 MVVM。
- 采用 MVVM 时，ViewModel 管理界面状态和命令；业务处理按需要放入功能类或服务。焦点控制、窗口拖动、动画等纯界面行为仍可放在 code-behind 中。
- 不默认引入复杂分层、模块化、DI 容器或导航框架，不为简单操作机械地增加封装层。

### 2.2 第三方依赖

- 优先沿用项目已有依赖。
- 新增依赖前先询问用户，说明用途、必要性及可行的替代方式；用户已明确同意的同一项依赖不重复询问。
- CommunityToolkit.Mvvm 等库不作为默认依赖。需要采用时按上述流程处理，其必需的源码生成和 `partial` 用法适用相应例外。

### 2.3 命名空间

- 统一使用块命名空间，大括号独占一行。
- 不使用文件范围命名空间：`namespace Example;`。

```csharp
namespace Example
{
    // 类型定义放在命名空间内部。
}
```

### 2.4 文件与类的划分

- 通常每个类或接口单独放在一个文件中。
- 明确只为某个类服务的辅助类，可以与该类放在同一个文件中。
- 除框架或源码生成器必需的情况外，人工维护的类型不主动拆分为多个 `partial` 文件，即使类型很长。
- WPF 的 XAML 配套类，以及框架或源码生成器要求的类型，允许使用必需的 `partial`。
- 类中存在明确的功能分组时，可以使用 `#region` 划分。

## 3. 命名规范

原则上遵循 C# 推荐命名规则，并执行以下具体约定：

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| `private` 字段（含静态字段，不含常量） | 单下划线开头的小驼峰，不另加 `s_` 前缀 | `_currentIndex` |
| `private` 属性 | 单下划线开头的小驼峰 | `_isReady` |
| 非私有属性 | 大驼峰 | `CurrentIndex` |
| 方法 | 大驼峰 | `LoadItems` |
| 异步方法 | 大驼峰，以 `Async` 结尾 | `LoadItemsAsync` |
| 类、结构、记录类型 | 大驼峰 | `ItemService` |
| 接口 | 以 `I` 开头的大驼峰 | `IItemService` |
| 参数、局部变量 | 小驼峰 | `itemCount` |
| 常量（含私有常量） | 大驼峰 | `MaxRetryCount` |
| 枚举及其成员 | 大驼峰 | `ExportMode.Selected` |
| 泛型类型参数 | `T` 或以 `T` 开头的有意义名称 | `TItem` |
| XAML 对象名称 | 有意义的大驼峰 | `SearchBox` |

- 通常不直接公开可变字段，通过属性或方法表达访问。
- 返回 `Task`、`ValueTask` 等异步结果的方法适用 `Async` 后缀；接口契约、框架规定名称及事件处理方法按其约束处理。
- 仅在代码、绑定、模板或动画等需要引用对象时设置 `x:Name`，不为每个控件机械命名。

## 4. 注释与文档

### 4.1 C# XML 注释

- 注释以中文为主，API、类型名称及必要术语保留准确原文。
- 所有人工编写的类型和成员均应提供完整的 XML 注释，包括类、接口、结构、记录类型、构造函数、方法、属性、字段、事件、枚举及其成员、嵌套类型等，私有成员同样适用。
- 自动生成文件不要求手工补注释；生成类型中的人工编写部分仍遵守注释规则。
- 接口实现和重写成员也应逐处写出完整注释，不用 `<inheritdoc />` 替代。
- `summary` 说明用途及必要的行为语义；有参数时写 `param`，有泛型参数时写 `typeparam`；有返回值的方法、委托等写 `returns`，属性值按需用 `value` 说明。
- 返回 `Task`、`ValueTask` 的方法说明异步完成的含义；返回 `Task<T>`、`ValueTask<T>` 的方法还应说明结果。
- `exception` 按需说明调用方需要知道的契约相关异常；`value`、`remarks` 等标签按信息需要使用，不机械堆砌。
- 位置参数 `record` 的语义通过类型注释和 `param` 说明，不手改编译器生成的成员。
- 修改行为时同步更新注释，避免注释与实现不一致。
- `<summary>` 的起始标签、内容、结束标签分别占行。
- 其他 XML 标签如无必要，标签和内容写在同一行。

```csharp
/// <summary>
/// 根据项目标识查找名称。
/// </summary>
/// <param name="itemId">项目标识。</param>
/// <returns>项目名称；不存在时返回 null。</returns>
private string? FindItemName(int itemId)
{
    return _itemNames.TryGetValue(itemId, out string? itemName) ? itemName : null;
}
```

> 此处仅演示成员注释与排版，不是完整的可运行类型。

### 4.2 XAML 区块注释

- 对成块的主要内容添加注释，清楚说明该区块的功能。

```xml
<!-- 操作区：提供刷新和保存入口。 -->
<StackPanel Orientation="Horizontal">
    <Button Content="刷新" Command="{Binding RefreshCommand}" />
    <Button Content="保存" Command="{Binding SaveCommand}" />
</StackPanel>
```

## 5. C# 排版与表达方式

### 5.1 基础排版、编码与行尾

- 使用 4 个空格缩进，不使用 Tab 缩进。XAML 同样适用。
- C# 命名空间、类型、方法和控制流块采用 Allman 风格，大括号独占一行；即使分支或循环体只有一条语句，也保留大括号。
- 文本文件采用 UTF-8。BOM 遵循仓库明确约定，没有约定时默认无 BOM。
- 行尾遵循仓库中适用于相应文件类型的 `.editorconfig`、`.gitattributes` 等明确约定；缺少约定时，C#、XAML 采用 CRLF，并在统一风格迁移时消除同类文件中的混合行尾。
- Git 的存储行尾和工作区行尾可以按配置不同；确保编辑器设置与 Git 属性相容，避免反复转换。
- 清理无意义的行尾空格，文件末尾保留一个换行，不堆积多余空行。
- 原始字符串、文本资源或其他内容中的空白如果影响实际数据，按语义保留，不机械清理。
- 局部变量右侧已清楚体现类型时可以使用 `var`；否则使用显式类型。

### 5.2 单行与换行规则

| 场景 | 规则 | 已有例外 |
| --- | --- | --- |
| 方法签名 | 无论长度和参数数量，均不换行 | 不设置按行长自动折行的例外 |
| `if` 条件 | 无论长度，均不换行 | 指条件表达式，不是要求整个语句体占一行 |
| 方法调用 | 普通参数列表无论长度和参数数量，均不换行 | 允许下述复杂参数结构自身换行 |
| 三目运算 | 不换行 | 不设置按行长自动折行的例外 |
| LINQ 表达式 | 可以换行 | — |

- 调用参数中的对象初始化器、多行 Lambda、集合初始化器或集合表达式、`switch` 表达式、原始字符串等，允许其结构自身分行。
- LINQ 表达式可以分行，作为调用参数时同样允许其表达式自身分行。
- 不为缩短代码行或单纯拆分表达式，提取只使用一次且没有复用可能的局部变量或方法；只有存在复用可能时才进行这类提取。
- 上述规则约束为了组织表达式而进行的提取，不影响资源释放、状态保存等语义本身需要的变量。

### 5.3 输入参数与枚举

- 当输入参数的可选值比较固定时，优先使用枚举，而不是用字符串约定这些取值。
- 涉及外部输入、序列化或持久化时，处理未知枚举值及版本兼容问题，不把强制转换视为合法性校验。

### 5.4 分支与模式匹配

- 使用 `switch` 时，如果模式匹配与传统 `case` 均可实现功能，优先采用模式匹配。
- 模式匹配既可用于 `switch` 语句，也可用于 `switch` 表达式；本条不要求把所有分支都改写成 `switch` 表达式。

## 6. 正确性、异步与资源管理

### 6.1 空值与输入契约

- 判断空值时，优先使用 `is null` 或 `is not null`，避免使用 `== null` 或 `!= null`。
- 新项目启用可空引用类型；已有项目全面启用时，按实质性重构渐进推进。
- 对边界输入进行必要校验，不依靠可空标注代替运行时检查。
- 尽量避免使用空值宽恕运算符 `!`（初稿中的“非空断言”）。仅在具备可说明的非空保证，且可以极大精简代码时使用；不能用它掩盖未解决的空值路径。
- 使用了 `!` 时，应在编码完成后额外向用户汇报位置及非空依据。

### 6.2 异步、取消与后台任务

- 避免在 UI 线程使用 `.Wait()`、`.Result` 等同步等待异步任务，或直接执行明显耗时的工作。
- I/O 操作使用合适的异步 API；耗时 CPU 工作按需离开 UI 线程，不机械地把所有逻辑包进 `Task.Run`。
- 长时间运行或可由用户中止的操作，按需提供取消和进度；支持取消时传递 `CancellationToken`，正常取消与失败分别处理。
- 除必要的事件处理方法等场景外，不使用 `async void`。必要的 `async void` 入口也应处理异常。
- 异步任务的失败必须被观察和处理；启动后台任务时明确其生命周期、取消方式及失败处理方式。

### 6.3 异常与日志

- 不无说明地吞掉异常，不使用无说明的空 `catch`。
- 在能够恢复、转译为适当结果或明确处理异常的边界捕获异常；重新抛出原异常时保留原始堆栈。
- 给用户可理解的失败提示，同时保留必要的诊断信息。
- 日志不记录密钥、令牌等敏感数据；需要诊断上下文时进行适当脱敏。

### 6.4 资源与生命周期

- 妥善释放流等可释放资源，使用与其生命周期相匹配的 `using`、`await using` 或显式管理方式。
- 处理长期事件订阅、计时器、取消令牌源和后台任务，避免对象因订阅而无法释放。
- 窗口关闭时，按任务的预期生命周期停止或取消无用工作，避免后台逻辑继续访问已失效的界面。
- 优先清晰管理生命周期，不把弱事件或全局单例作为默认补救手段。

## 7. WPF 与 XAML

### 7.1 绑定、状态与命令

- 使用数据绑定时，按需要提供属性变化和集合变化通知；集合增删通知不能代替集合项自身的属性通知。
- 命令可执行状态应反映当前界面和业务状态；对保存、加载等操作明确是否允许重复触发，防止重复提交或状态交错。
- 按需求设置绑定更新时机和输入验证反馈，区分输入过程中的暂态无效值与提交错误。
- 相关命令应反映当前能否提交；输入不合法时给出明确反馈。
- 开发和验证时检查相关绑定错误、资源查找失败及状态更新问题。
- 上述规则在使用 code-behind 或 MVVM 时均按实际场景适用，不因架构较简单而省略必要的状态管理。

### 7.2 UI 线程

- 更新 WPF UI 对象和绑定集合时遵循线程归属及同步规则。
- 后台任务需要更新界面时，使用合适的调度方式返回 UI 线程；避免无意义的调度及跨线程访问。

### 7.3 标签排版

- 普通标签中的样式属性写在同一行，不分行书写。
- `Window`、`UserControl`、`Page` 等顶级标签中的样式属性分行书写。

### 7.4 布局、适配与性能

- 在 `StackPanel` 与 `Grid` 均可满足需求时，比较后续维护和扩展的便利程度，选择更合适的容器。
- 如果 `Grid` 没有明显优势，使用 `StackPanel`。
- 同时考虑尺寸约束、滚动和虚拟化；大列表避免因外层滚动容器或面板配置失去虚拟化。
- 检查窗口缩放、高 DPI、长文本及键盘焦点，不机械地给所有尺寸设置固定值。

### 7.5 样式、资源与视觉风格

- 样式尽量抽取为 `Style`，放在独立文件中。
- 优先抽取有复用或统一维护价值的样式，不为每个控件机械地建立一次性样式。
- 独立资源字典可以按控件、功能或主题组织，避免把所有样式堆进一个大文件。
- 根据资源是否需要在运行时更新，选择 `StaticResource` 或 `DynamicResource`。
- 可参考 Visual Studio 2022 Dark 风格或 Windows 原生风格。
- 用户没有特别指定时，使用 Windows 原生风格，不额外进行复杂的视觉设计。

### 7.6 图标绘制与资源组织

- 需要图标时，优先使用 XAML 绘制 Icon。
- 所绘制的 XAML 图标定义集中放在独立的图标资源字典文件中，例如 `Resources/Icons.xaml`，由需要的页面或控件通过资源引用使用。
- 项目已有独立的图标资源字典时沿用其组织方式；单次使用的 XAML 图标也应按本规则抽取。

## 8. AI 协作、验证与交付

### 8.1 需求澄清与修改准备

- 阅读项目约定、相关实现、目标框架和已有依赖，理解需求和当前行为。
- 在开发或构建过程中，发现需求模糊，或存在尚未明确选择的多种可行实现路径时，应及时提问，由用户选择；不能等到对应实现完成后再询问。
- 提问时说明需要决定的问题、可选方案及其差异，可以给出推荐理由。得到答复前暂停依赖该选择的实现，可继续不依赖该选择的工作。
- 已确认的同一事项或用户已明确授权自行决定的事项，不重复询问；按已有决定执行。
- 新增依赖遵循第 2.2 节，规范和当前项目约束无法兼容时明确说明冲突，不悄悄跳过规则。
- 涉及配置存储、数据库、网络、破坏性操作、性能目标或发布部署等项目特有问题时，按 [项目场景](project-scenarios.md) 补充确认。

### 8.2 修改过程中

- 接入规范和统一迁移的范围按第 1.1 节处理；执行迁移时，功能改动与风格调整尽量便于分别审查。
- 不夹带无关的架构更新或实质性重构，不手工修改生成文件。
- 不编造 API、库能力或验证结论；不能确定的行为通过项目代码、可靠资料或实际验证确认。
- 同步维护注释、绑定引用及相关资源；不为满足外观规则改变程序语义。

### 8.3 验证深度

- 代码修改后构建受影响项目，并检查本次涉及的主要界面流程。
- 涉及业务规则、数据处理或缺陷修复时，按风险补充或运行有价值的针对性自动化测试。
- 纯排版和注释调整不机械新增测试；仍根据影响范围检查构建、引用与行为是否保持一致。
- 测试框架沿用已有方案；需要新增工具或依赖时遵循第 2.2 节。
- 测试数据尽量独立，不使用真实生产数据进行破坏性验证。
- 无法完成构建、测试或桌面界面检查时，说明原因及未验证范围，不把未执行的检查写成已通过。

### 8.4 完成后的汇报

- 说明实际改动及原因。
- 说明完成了哪些验证，以及失败或未验证的事项和原因；编译通过不等于界面行为已验证。
- 说明偏离规范的例外及依据。
- 若使用了空值宽恕运算符 `!`，额外列明位置及非空依据。
